Process

Telemetry flows from a Go simulator through Kafka into ClickHouse, and the dashboard reads it back in milliseconds

One store for logs and metrics. Every panel in this console shows how much ClickHouse read to answer it.

01

Ingest

A Go program emits JSON events for a fleet of services and Postgres clusters. Kafka buffers them, and ClickHouse consumes the topics with its Kafka engine.

02

Store

One MergeTree table per signal, sorted by service, severity and time, compressed column by column, expired by a 90-day TTL.

03

Query

The sort key and a sparse index let a search read only the ranges that match. Rows read and time are shown next to every result.

04

Time series

Materialized views keep per-minute rollups next to the raw rows, so 30 days of charts cost the same as 30 minutes.

05

Govern

Roles, row policies and quotas in the database, and every query lands in the query log.

Why ClickHouse for telemetry

  • Columnar storageRepetitive fields such as service, host and severity compress to almost nothing.
  • Sparse indexLow-cardinality columns first in the sort key skip most of the data for a time-bounded search.
  • Rollups on insertMaterialized views aggregate while data arrives, no scheduled jobs.
  • Streaming inThe Kafka engine reads topics directly. No collector code on the database side.
  • Scale-outShared-nothing shards and replicas when one box is no longer enough.

What changes on the bill

  • Per coreEDB prices ClickHouse per core, not per GB or per query. Retention and cardinality stop driving the cost.
  • Open sourceUnmodified ClickHouse. No proprietary format, so you can migrate away freely.
  • SupportedEDB-signed packages, SLAs, CVE response and break/fix.
  • Your dataRuns in your environment, next to your Postgres estate and the open Iceberg catalog.
